# Create a Blog Post (visualsbyjoshua.com)

This skill exists because past passes on this site produced two recurring failure modes: (1) raw phone screenshots shipped as hero/credibility images, and (2) new blog posts that drifted from the shared design system because they were hand-rolled instead of built from the real template. Follow this in order. Do not skip the image-vetting step even under time pressure — it is what the earlier failures had in common.

## 0. Taste bar before anything else

This site's design contract lives in `DESIGN.md` (generated by the `impeccable` skill against 11 reference photographer sites — reesemoorephotography.com, mcgphotography.com, chrismanstudios.com, and others listed at the top of that file) and `design-verification.md` (the benchmarking pass). Read `DESIGN.md` before writing any new post copy or markup — it is the source of truth for color tokens, type scale, spacing, and component patterns, not this skill. Key non-negotiables pulled from it:

- **Palette**: background `#fcfbfa`, text `#2a2a2a`, accent tan `#be976d` (backgrounds/borders/large CTA text) / hover `#a67f5a`, card bg `#f5f3f0`, borders `#e8e8e8`/`#d8d8d8`. For small text set in the accent (kickers, prices, inline links), use `#856545` instead of the base tan; `#be976d` only clears 2.7:1 against white, which fails WCAG AA for text. On dark backgrounds (`#2a2a2a` or darker), use the lighter `#be976d`, not `#856545` (the darker shade drops to 2.7:1 there too, just against black instead of white). Never introduce a new color outside this palette. Use `var(--primary)`, `var(--secondary)`, `var(--muted)`, `var(--light)`, `var(--shadow)`, `var(--transition)` from `styles.css`, not hex literals, wherever the token already covers the case.
- **Type**: Cormorant Garamond (serif, display/headings, often italic) + Inter (sans, UI/body). Headings use `clamp()` fluid sizing, not fixed px. Give parallel/sibling headings (gallery caption titles, card titles) a consistent level with no skipped step from the section's own `h2`; a lone `h4` directly under an `h2` with no `h3` between them is a real WCAG 1.3.1 violation, not a style choice.
- **Voice**: editorial magazine, first-person from Joshua, specific and concrete (real settings, real technique, real moments), never generic AI-marketing copy ("elevate your brand," "capture the magic"). Read two or three existing posts in `blog/` before writing new copy to match register. Use active voice, address the reader as "you," vary sentence length for rhythm, and cut hedging words ("might," "could") when the claim is actually certain. No em dashes, no semicolons, no emoji, anywhere in visible copy: rewrite as two sentences, a comma, or a colon instead.
- **Components**: 10px border-radius, minimal shadows (0-2px, only on hover), 0.3s transitions, image hover zoom to ~105%. Reuse existing component classes (`.streetwear-gallery`, `.technique-card`, `.lighting-tip`, `.about-container`, `.location-highlight`) rather than inventing new ones. Grep `blog/*/index.html` for a post covering a similar subject (event vs. portrait vs. editorial) and copy its structure, don't design from scratch. Do NOT copy a `border-left` onto `.technique-card`/`.lighting-tip`/`.pro-tip`/`.faq-static` even if an older post in the repo still has one: a thick colored left border on a card is a named AI-design tell (`impeccable`'s detector calls it `side-tab`) and was stripped from every post that had it. The shared `styles.css` `.technique-card` definition has no border; match that, not a stale inline override.

`impeccable` and `taste` (frontmatter name `design-taste-frontend`) are committed into this repo under `.claude/skills/impeccable/` and `.claude/skills/taste/` — check the skills list in your system reminder and invoke them (`impeccable audit`/`impeccable critique` for the schema-driven pass, `taste`'s pre-flight checklist for the anti-slop scan) before publishing. That's the portable fix for a skill that only lived on one machine: commit its `SKILL.md` (and, as it turned out for `impeccable`, its `reference/*.md` and `scripts/*.mjs` — it isn't a single-file skill) into the repo so any session opened against it, local or cloud, has it. Each skill MUST live in its own named subdirectory (`.claude/skills/<name>/SKILL.md`) — a `cp -r` into a not-yet-existing `.claude/skills/` once landed `impeccable`'s `reference/` and `scripts/` as flat siblings of a bare `.claude/skills/SKILL.md`, and the skill silently stopped appearing in the skills list at all until it was moved into `.claude/skills/impeccable/`. If a future session finds either skill missing, check `.claude/skills/` for exactly this pattern before assuming a fresh checkout. The `taste bar` principles above remain the fallback summary if you're ever working from DESIGN.md alone without the skills loaded.

## 1. Vet the source images before doing anything else

Real failures found in this codebase: raw Photos-app screenshots used as the site's flagship credibility image and a portfolio card; a proof-sheet/contact-grid export used directly as an og:image; a bad manual crop reducing a portrait to a 171px-tall sliver. Do not repeat these.

For every image in the new set:
- **Open and actually look at it** (Read tool renders images — use it, don't just check file size/dimensions).
- **Reject phone-camera-roll or Photos-app screenshots.** Signs: visible OS chrome, a grid of thumbnails, share-sheet UI, aspect ratios matching a phone screen (~9:19.5) rather than a camera sensor (3:2, 4:5, 4:3, 1:1).
- **Contact-sheet / proof-gallery grids are usable but degraded.** If the client exports a Pixieset-style 3-column grid instead of individual files, you can crop a single cell out (see step 2), but flag clearly to the user that the result caps out at roughly `native_width / columns` pixels wide — too soft for an eager-loaded hero or the site's primary og:image unless that's explicitly accepted. Never silently downgrade an already-good, high-visibility image (homepage hero, sitewide og:image) to a low-res crop — pause and ask first, the way this session did for `cypress-gardens-engagement-shoot.webp` before the user explicitly said it was fine.
- **Check orientation.** `ImageOps.exif_transpose()` before saving — a source with no EXIF orientation tag but pixels genuinely stored sideways (this happened with a headshot source) will not be fixed by transpose; you have to eyeball it.
- **Prefer an existing correct asset over a mediocre new one.** Before processing a "replacement," grep for whether a better image already lives on the site unused (this happened with a headshot — the correct photo already existed at `headshot1.webp`, so the fix was deleting the broken one and repointing references, not processing a new file).

## 2. Process images into the site's derivative convention

Source files live either at the site root, under `images/<category>/`, or (for posts) under `blog/<slug>/*.webp`. Derivatives live under `images/optimized/<group>/<base>-<width>.<ext>`, where `<group>` is `posts/<slug>` for a blog post, or the category folder name (`couples`, `concerts`, `home`, etc.) for a source that lives elsewhere.

The real pipeline is `_private/build/optimize-images.mjs` (Node + sharp — `mkdir -p ~/.visualsbyjoshua-build && cd ~/.visualsbyjoshua-build && npm install sharp@latest`, then `node _private/build/optimize-images.mjs`). It scans every HTML/CSS reference and only regenerates what's missing or stale — run it after wiring the HTML instead of hand-rolling derivatives, when sharp is available.

When sharp isn't available (e.g. this sandbox), replicate its contract with Pillow — same widths, same quality targets, same "never upscale" rule:

```python
from PIL import Image, ImageOps

WIDTHS = [400, 800, 1200, 1600]

def gen(src_path, out_dir, base):
    im = ImageOps.exif_transpose(Image.open(src_path))
    if im.mode != 'RGB':
        im = im.convert('RGB')
    targets = [w for w in WIDTHS if w <= im.width] or [im.width]
    for w in targets:
        h = round(im.height * (w / im.width))
        r = im.resize((w, h), Image.LANCZOS)
        r.save(f'{out_dir}/{base}-{w}.jpg', 'JPEG', quality=80, optimize=True)
        r.save(f'{out_dir}/{base}-{w}.webp', 'WEBP', quality=80, method=6)
        r.save(f'{out_dir}/{base}-{w}.avif', 'AVIF', quality=62)
```

Rules that matter:
- **Never upscale.** If the source is smaller than 400px wide, emit one derivative at its native width and use that width in every `srcset`/`sizes`/`width`/`height` attribute — do not list a 400w/800w/1200w srcset that doesn't exist on disk (this was a real bug introduced and then fixed in this session).
- **`width`/`height` attributes must match the actual served file's real pixel dimensions**, even when CSS overrides the display box with `object-fit: cover` — they're still a layout hint, and copy-pasting a stale value from another card is an easy, easy-to-miss mistake (also happened this session, via an overly broad `sed`).
- **Cropping a cell out of a contact-sheet grid**: detect gutters by scanning row/column brightness (rows/columns near-black are gutters between cells), crop the target cell, then inset another 15-20px inward — the rounded-corner mask on each cell leaves visible black corner fragments otherwise.

## 3. Write the post from the real template, not from memory

Copy the full HTML structure from an existing post covering a similar subject — do not reconstruct the shell from general knowledge of "what a blog post looks like." Good templates to copy from by subject type:
- **Event/culture piece with a photo gallery**: `blog/streetwear-popup-photography-we-on-the-streets/index.html` or `blog/record-store-editorial-fashion-photography/index.html`
- **Technique/settings-heavy piece**: `blog/concert-photography-gza-wu-tang/index.html`
- **Location/couples piece**: `blog/anniversary-photography-downtown-charleston/index.html`

Required pieces, all present in every existing post — do not ship a post missing any of these:
1. Full `<title>`/meta description/canonical/robots block.
2. `og:*` and `twitter:*` tags, image pointing at a real derivative (not the raw multi-MB source).
3. `BlogPosting` JSON-LD (headline, description, author `@id` referencing `https://visualsbyjoshua.com/#person`, publisher with logo, `datePublished`/`dateModified`, `image`, `mainEntityOfPage`, `keywords`).
4. `BreadcrumbList` JSON-LD, matched by a **visible** `.breadcrumb` div in the hero (Home → Blog → Post title) — the two must agree; this site had a real bug where breadcrumb schema existed with no matching visible UI.
5. `<section class="article-hero hero-bg" style="--bg-url: url('...');" id="main">` — using the `hero-bg`/`--bg-url` pattern, not a hand-rolled inline background (the undefined-`--bg-url` bug was a real, sitewide-breaking regression earlier in this project).
6. Standard nav, footer, back-to-top script, mobile hamburger script, `analytics.js` — copy verbatim from the template post.

## 4. Wire it into the site

A post that exists only at its own URL is invisible. Every new post needs:
- **A card in `blog.html`**: inserted into `.blog-grid`, `data-category` matching one of the existing filter buttons (`portraits`, `events`, `locations`, `couples`, `concerts`, `graduations`, `greeklife`, `business`, `education` — reuse, don't invent a new one unless a matching filter button doesn't exist), using a `<picture>` block pointing at the post's own derivatives.
- **A `sitemap.xml` entry**: `<url><loc>.../blog/<slug>/</loc><lastmod>YYYY-MM-DD</lastmod><changefreq>monthly</changefreq><priority>0.7-0.9</priority></url>` — priority 0.9 for a flagship/location-guide post, 0.7 for a standard feature.
- Check whether any *other* page should link to it (a relevant service page's "Related reading" list, another post's internal links) — grep for the subject matter across `blog/` and service pages before assuming the new post is an island.

## 5. QA before calling it done

- Parse-check every touched file: `python3 -c "import html.parser; ..."` (error callback prints parse errors) — cheap, catches unclosed tags immediately.
- Validate every `<script type="application/ld+json">` block with `json.loads()` — a schema syntax error fails silently in the browser.
- Serve locally (`python3 -m http.server`) and screenshot with Playwright (`/opt/pw-browsers/chromium-*/chrome-linux/chrome`, needs a `package.json`/`node_modules` alongside the script — see any prior `scratchpad/*.mjs` in this session's temp dir for a working invocation).
- **Known false-positive**: a `fullPage` screenshot taken right after `networkidle` can show `loading="lazy"` images below the original viewport as solid black (the `.streetwear-image` background color, no bug, image never got its lazy-load trigger before the resize). Before treating a black image box as a real bug, scroll each image into view individually and recheck `img.complete`/`naturalWidth` in `page.evaluate()` — if those come back populated, it was a screenshot artifact, not a site bug.
- Real external CDN calls (Google Fonts, Font Awesome CDN, EmbedSocial) frequently fail inside this sandbox with `ERR_TUNNEL_CONNECTION_FAILED`/`ERR_CONNECTION_RESET` — that's sandbox network policy, not a production bug. Don't chase it.

## 6. Commit

One commit per logical unit of work (image fixes separate from new-post-authoring separate from site-wiring, unless small enough to combine sensibly). Write the "why," not the "what" — the diff already shows the what.
